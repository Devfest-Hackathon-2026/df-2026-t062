58〜60は共通項目で、全62項目の内訳で重複しない。61・62は書類だけでは判断できない。対象外／書類なし／書類だけでは判断不可を分け、未点検の書類ごとの項目数を表示する。他書類の存在だけで、その項目を適合とはしない。

点検・履歴・最新判定は書類IDで固定する。第4・5表は最新の別記録へ置き換えない。第1〜3表では同じ計画版の別表と主なアセスメントを参考にするが、その項目は今回の点検数に含めない。参考書類の保存版と未保存値の有無を結果に表示する。

画面の未送信入力は下書きAPIへ送ってから点検する。ニーズ・週間予定も現在の構造から読み取り専用で射影する。点検を理由とする保存版・確認済み・正式確定は作らない。参考資料を含む値と様式版の指紋で、その後の変更を検出する。

全対象を判定でき、不足がなければ適合。不足があれば要確認。対象0件や一部未判定で不足もなければ判定保留。カテゴリが1〜2個の書類は棒、3個以上はレーダーで表示する。PCの常設パネルとタッチ画面のダイアログで同じ結果を使う。

37番の長期目標期間が認定有効期間外・逆順なら、AIが適合と答えても不足にする。不正日付・一部不明の期間は機械的な適合の根拠に使わない。

## モニタリング様式

アプリ独自のA4簡易様式を `forms/originals/build-monitoring.py` で作成。指定の行政・団体様式ではない。埋め込みフォント、固定メタデータによる再生成の同一SHAを確認した。

`form_kinds`、様式版、利用者の書類の作成・保存・PDFの既存機構を使う。既に同じkindがあれば設定を上書きしない。新様式を既存書類へ自動リベースしない。原紙の公開例外は本プロジェクトが作成した1ファイルだけ。

## 変更箇所と導入

- `0043_document_inspections.sql`: 対象書類・結果の移動先ID、対象単位の実行中重複防止。完了済みの旧アセスメント点検は対象を復元し、旧実行中ジョブは終了時に対象を記録する。
- `0044_monitoring.sql`: 書類の種類。`db:migrate --forms` で様式版も登録し、既存リリース手順の `forms:assets` で原紙・ページ画像を配置する必要がある。
- `worker/inspect/collect.ts`、`db/inspections.ts`: 事業所と利用者を検証、同一スナップショット、対象と参考の区別、履歴とcoverage。
- `core/checks/mhlw-careplan.json`: 33〜60の欄・ガイド。元の項目と段階基準は変更しない。
- `PetInspection`、`CarePlanArea`、`CareRecordWork`、PC/Pad画面: 対象を渡し、同じ入力欄へ戻る。

## 検証と限界

ローカルの隔離DBと架空データを使用。本番DB・本番データ・外部AI呼び出しは使用しない。

- 最新main統合後のNode全テスト547件成功。開いた第1〜5表の対象項目、古い記録の固定、期間外判定、権限、同時開始の重複防止、未対応書類の0件・判定保留、モニタリング保存・PDF文字を検証。
- `inspection-documents.spec.ts`: 第2表未保存入力の送信と保存版不変、別表の履歴、古い支援経過、モニタリングの作成・保存・再表示・PDF、結果から同じ欄への移動。
- 型検査・様式チェック・ビルド。モニタリングの印字済みPDFを画像化し、文字と罫線の収まりを目視確認。
- ブラウザ結果はPR本文に最終件数を記録する。iPad相当はWebKitエミュレーションで、実機Safari・キーボードの検証ではない。

DB/API/UIのAIはfakeで対象・接続・保存の安全性を検証した。追加の実Gemini検証は[品質レポート](../verification/document-inspection-real-gemini.md)に分けて記録した。12回・延べ62判定中59一致だが、第2表で3項目の不足見落とし（うち1項目は基準解釈の専門職確認が必要）があり、ユーザーの指示により実装PRはマージし、改善・再検証と未実施の実機確認は[Issue #246](https://github.com/cloud0327/df-2026-t062-dev/issues/246)に引き継ぐ。医学的・制度的な正式な適否を保証するものではない。点検は記録された事実だけを扱う。単一の支援経過だけで月全体の訪問・連携実績を断定しない。図そのものの読み書きは引き続き #132 の対象。
