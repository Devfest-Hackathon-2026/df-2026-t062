## 調査した処理経路

`AGENTS.md`、[`api/care-plan-ai.ts`](../../api/care-plan-ai.ts)、[`api/server.ts`](../../api/server.ts)、[`api/app.ts`](../../api/app.ts)、[`db/care-plans.ts`](../../db/care-plans.ts)、[`test/care-plan-api.test.ts`](../../test/care-plan-api.test.ts)、[`docs/ケアプラン仕様.md`](../ケアプラン仕様.md)、[`core/care-plan-slot.ts`](../../core/care-plan-slot.ts)、[`CarePlanWork.tsx`](../../src/components/care-plan/CarePlanWork.tsx)、[`e2e/care-plan.spec.ts`](../../e2e/care-plan.spec.ts) と関連スキーマを確認した。

1. 保存済みassessmentのdocument/revisionを指定して `POST /api/care-plans/:planId/ai-drafts`。
2. `createCarePlanAiDraft` が同一事業所・利用者・assessment種別・保存版を検証。現在の未保存値ではなく指定revisionを読む。
3. `geminiCarePlanDrafter` が `{clientName, savedAt, assessment: source.values}` を実Geminiへ送信。既存の計画内容はモデルへの入力に含めない。
4. 最初の `{`〜最後の `}` を抽出して `JSON.parse`。`normalizeAiProposal` は最上位の型と配列だけを検証。JSON Schemaによる深い出力制約はない。
5. 原案は `proposed`、例外・不適切な最上位構造は `failed` で保存。参照revisionとprompt version `care-plan-draft-v2` を固定し、計画へ自動適用しない。
6. 明示的なapply APIが第1表の人の入力・非空値を保護。第2表に新規ニーズ・目標・サービスを作成し、その時作ったサービスだけに `serviceRef` を対応させる。
7. 第3表は `AiPlanSlotSchema` と `validatedSlots` で時刻・期間・重複・重なり等を検査。不適切な候補は `skipped`。適用後も計画は `draft` であり、保存・確定は別操作。

本番drafterはfinishReason・モデルメタデータを検査/永続保存していない。原案テーブルへのINSERTはmodel列を設定せず、使用量・responseId・レイテンシも残さない。本レポートの計測は検証コードの観測による。今回の変更はレポート・再現データ・検証コードのみ。
