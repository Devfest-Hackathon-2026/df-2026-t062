## 修正内容・移行

- 採用UI・クライアントは `key + base` のみ送る。サーバーは保存候補の値を使う。互換性のため `value` が送られても完全一致だけ許可し、差し替えは400。保存候補の型・根拠ID・不確実性も確認する。
- 開始時の `template_version_id` を記録し、workerはその版で候補を生成する。採用では対象書類をロックして版を照合し、違えば409。再度同じ原本を選ぶと新しい版で候補を再生成する（原本・読取済みページは再利用、様式に依存する要約は破棄）。
- `0009_document_input_form_version.sql` は版の外部キーと `upload_generation` を追加する。既存原本は世代1の `/original` を維持。既存候補の版は推測せずNULLとし、採用前に再生成を求める。候補・原本・採用履歴は移行で消さない。
- ファイル名全体で移行履歴を管理する既存runnerに従う。`0006_care_plans.sql`・`0007_care_plan_saved_structure.sql` の入った最新mainでも移行をテスト済み。依存先は既存の `document_inputs` と `form_template_versions` のみ。
- 適用順はDB追加移行→API／workerの切替。旧workerは新しい世代パスを読めないため、新APIで再送を受け付ける前に旧workerを停止・排出する運用が必要。混在デプロイや本番移行は実施していない。
- ハッシュ・サイズ・署名で拒否した原本、期限切れURLの再発行は別世代へ送る。正常原本は再送しない。完了確認は行ロックの取得後に最新世代を読む。古い送信が遅着しても新世代に混ざらない。削除はDB確定後、拒否した旧世代だけを対象とする。
- startで見つかった壊れた原本や、期限切れ後に遅着した旧世代は置き場に残り得る。DBからは参照しないが、保存期間・不要世代の運用上の掃除は別途必要。GCSの実通信・障害時の孤立セッション掃除は未検証。

## ブラウザ確認（手動＋DOM操作、全自動E2Eではない）

Chromium、隔離スキーマ `e2e_155_doc`、専用LocalStorage、架空PNG、合成のreader／summarizer／writer応答だけを使用した。通常の `AI_PROVIDER=fake` は原文を読まず空候補を返すため、候補を返す検証用依存を差し込んだ。本番fakeの動作は変えていない。

1. 架空の佐藤さんを開き、「書類を取り込む」へ移動。
2. DOMのFile入力へ架空PNGを設定してchangeイベントを発火。実際の添付処理・アップロード・完了API・worker・一覧の再取得を通って「確認できます」と3候補が出ることを確認。
3. 「食事摂取」を外し、移動と相談経路だけをUIの反映ボタンで採用。`by=cm`、保存候補の値と原本出典、外した欄が未入力であることをAPIでも照合。
4. ページを再読込。用紙の相談経路に「地域包括支援センターから」、移動の第3選択肢に丸が残ることをDOMで確認。
5. 候補と異なる「全介助」を採用APIへ直接送信し、400と「候補と違う値は反映できません」を確認。
6. 読取後に別リクエストで食事を「全介助」に変更し、古い候補をUIから反映。競合409の案内を確認。
7. 別PNGの候補で赤の「−全介助」、緑の「＋見守り等」を確認。計算済み文字色は `rgb(143,33,33)`／`rgb(23,83,47)`。候補の編集用入力欄は0件。
8. 同じ利用者の入院時情報提供書を作り、反映前のfieldsを記録。新候補の食事だけ反映し、対象欄が見守りになり、他書類のfieldsが不変であることを照合。
9. サイズだけ同じ壊れたPNGを送信し、completeの400を確認。同じ正しいPNGをFile入力に設定し直すと、同じ取込IDで再送・読取を経てreviewへ回復することを確認。
10. 最新mainへの移植後、追加移行を適用してAPIを再起動。新しい架空PNGの添付→3候補→UI反映→「書類に反映しました」まで再確認。

制限：OSネイティブのファイル選択ダイアログの自動操作は未確認。ブラウザの幅は431 CSS pxで、DOM経由のスクロール・クリックを併用した。標準PC幅・iPadでの視認性と操作性の完全な再確認は未実施。今回のキャプチャはvisible-tab制約で取得できず、赤緑はDOMと計算済み色で確認した。専用置き場に様式背景画像は生成していないため、用紙の確認は入力オーバーレイと選択状態に限定する。実Gemini、実手書き・実写真、処理地域、ケアマネの時間実測・受け入れ承認を満たしたとは扱わない。

## 再確認用API

`eval/document-import/browser-server.ts` は、同じ合成応答を再現するローカル専用入口。先に新規の隔離スキーマを作り、次の環境変数をそのシェルで設定する（既存・本番DBのスキーマを指定しない）。

```sh
export DATABASE_URL=postgres://postgres:postgres@localhost:54329/careman
export DB_SCHEMA=e2e_document_input_review
export LOCAL_STORAGE_DIR="$PWD/.data/e2e_document_input_review/storage"
export AI_PROVIDER=fake
node db/migrate.ts --forms
node db/seed.ts
PORT=8788 node eval/document-import/browser-server.ts
```

別のシェルで `API_ORIGIN=http://127.0.0.1:8788 npm run dev -- --port 5181` を開始する。`kato@example.com`で入り、架空のPNGだけで上記の導線を確認する。このAPIは添付内容によらず決まった架空の候補を返すので、読取精度の評価には使わない。
